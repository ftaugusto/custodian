  • IBM Cloud Container Registry — stores the custodian image
  • IBM Code Engine — runs the job and the webhook application
  • IBM Secrets Manager — stores API keys and secrets
  • IBM Activity Tracker (Event Routing) — routes audit events

  • IBM Event Streams (optional) — Kafka bus for multi-consumer fan-out
  • IBM Security and Compliance Center Workload Protection (optional)

4.Scheduled sweep — Code Engine job

A scheduled job runs all policies on a fixed cadence. It acts as a safety net that catches anything the event-triggered pipeline may have missed. every 15 min

ibmcloud ce project select --name custodian-prod

ibmcloud ce job create \
  --name custodian-sweep \
  --image us.icr.io/custodian/c7n-ibmcloud:latest \
  --argument run \
  --argument "--configs=/app/policies/" \
  --argument "--output-dir=/tmp/c7n-out" \
  --argument "--cache-period=300" \
  --env-from-secret custodian-secrets \
  --env IBMCLOUD_REGION=us-south \
  --cpu 1 --memory 2G --maxexecutiontime 1800

ibmcloud ce jobrun schedule create \
  --name custodian-sweep-schedule \
  --job custodian-sweep \
  --schedule "*/15 * * * *"
Tip — scoped sweeps. For large accounts, create a separate scheduled job per policy file (cos.yaml, vpc-networking.yaml, …) so each run completes faster and failures are isolated.

5.Near-real-time enforcement — event-triggered pipeline

End-to-end latency: ~60–90 seconds from the API call that creates or modifies a resource to the policy check completing.

5.1 Architecture overview

IBM Cloud API call │ ▼ Activity Tracker (Event Routing) routing rule: action starts with "cloud-object-storage" / "is." / "power-iaas" … │ ▼ Event Notifications topic → subscription → webhook │ ▼ Code Engine application (custodian-webhook) • parses the AT event payload • maps action → policy file • runs: custodian run --configs /app/policies/<file>.yaml --cache-period 0 │ ▼ IBM Cloud APIs (query + remediate) │ ├──► tag / stop / delete resource └──► write finding to SCC WP

5.4 Code Engine webhook application

The webhook is a small HTTP server that receives Event Notifications payloads, maps the action field to a policy file, and runs custodian in a background thread so the HTTP response is immediate.

ibmcloud ce application create \
  --name custodian-webhook \
  --image us.icr.io/custodian/c7n-ibmcloud:latest \
  --command python3 \
  --argument /app/webhook/app.py \
  --env-from-secret custodian-secrets \
  --env IBMCLOUD_REGION=us-south \
  --env POLICY_DIR=/app/policies \
  --env OUTPUT_DIR=/tmp/c7n-out \
  --min-scale 1 --max-scale 5 \
  --cpu 1 --memory 2G --port 8080

Key logic in webhook/app.py:

ACTION_TO_POLICY = {
  "cloud-object-storage":  "cos.yaml",
  "is.instance":           "vpc-compute.yaml",
  "is.volume":             "vpc-storage.yaml",
  "is.security-group":     "vpc-networking.yaml",
  "is.network-acl":        "vpc-networking.yaml",
  "power-iaas":            "powervs.yaml",
  "kms":                   "kms.yaml",
  "containers-kubernetes": "kubernetes.yaml",
  "databases-for-":        "dbaas.yaml",
  "iam-identity":          "iam.yaml",
  "iam-groups":            "iam.yaml",
}

def do_POST(self):
    payload = json.loads(body)
    action = payload.get("data", payload).get("action", "")
    policy_file = next(
        (f for p,f in ACTION_TO_POLICY.items() if action.startswith(p)), None)
    if policy_file:
        threading.Thread(target=_run_custodian,
                         args=(policy_file, action), daemon=True).start()
    self.send_response(200); self.end_headers()

6.Event Streams (Kafka) integration

Use IBM Event Streams when you need audit-event fan-out to multiple consumers (SIEM, data lake, custodian) from a single Activity Tracker route, or when you need replay and retention beyond what Event Notifications provides.

Activity Tracker (Event Routing) │ target: Event Streams ▼ Event Streams topic "at-audit-events" │ ├──► SIEM / Splunk / QRadar consumer ├──► Data lake / COS archive consumer └──► custodian-kafka-consumer (Code Engine job) │ ▼ custodian run --cache-period 0
ibmcloud atracker target create \
  --name custodian-kafka-target \
  --type event-streams \
  --brokers "$KAFKA_BROKERS" \
  --topic at-audit-events \
  --api-key "$KAFKA_API_KEY"

The Kafka consumer job (kafka_consumer.py) connects with SASL_SSL / PLAIN, reads from auto_offset_reset=latest, maps each event's action field to a policy file, and calls custodian run. A seen_policies set prevents launching duplicate runs for the same policy file while one is already executing.

7.SCC Workload Protection webhook

SCC WP raises a finding → notification channel (webhook) → custodian webhook receiver → scoped custodian run.

SCC Workload Protection finding │ Notification channel (webhook type) ▼ Code Engine application (custodian-webhook, path /sccwp) │ maps finding.kind → policy file ▼ custodian run --cache-period 0 │ ▼ SCC Findings API (write-back — optional)

Configure the SCC WP notification channel

  1. Go to Settings → Notification channels in SCC WP console.
  2. Click Add channel, choose Webhook.
  3. Set URL to the Code Engine application URL with path /sccwp.
  4. Choose finding types: STORAGE → cos.yaml, NETWORK → vpc-networking.yaml, IAM → iam.yaml, RUNTIME → vpc-compute.yaml.
SCC WP finding kindPolicy file triggered
STORAGEcos.yaml
NETWORKvpc-networking.yaml
IAMiam.yaml
RUNTIMEvpc-compute.yaml
KMSkms.yaml
CONTAINERkubernetes.yaml

Write findings back to SCC

After a policy run, parse resources.json from the output directory and POST each matched resource as a finding to the SCC Findings API (https://us-south.secadvisor.cloud.ibm.com/findings/v1/<account>/providers/custodian/notes). This creates a closed loop: SCC WP → custodian → SCC findings.

8.IAM service-to-service authorisations

Create a service ID custodian-runner and assign these policies:

All governed services (COS, VPC, KMS, IKS, DBaaS, PowerVS, IAM)Viewer + Writer

ibmcloud iam service-id-create custodian-runner \
  --description "Cloud Custodian policy runner"

for SERVICE in cloud-object-storage is kms containers-kubernetes \
               databases-for-postgresql databases-for-mysql \
               databases-for-mongodb databases-for-redis \
               databases-for-elasticsearch databases-for-rabbitmq \
               power-iaas; do
  ibmcloud iam service-policy-create custodian-runner \
    --roles Viewer,Writer --service-name "$SERVICE"

  --roles Writer --service-name global-tagging

  --roles SecretsReader --service-name secrets-manager \

9.Outputs and findings

Each policy that matched resources writes to --output-dir/<policy-name>/:

  • resources.json — full resource objects that matched
  • actions.json — actions taken and their results
  • metadata.json — run metadata (timestamp, count, duration)

Persist outputs to COS

ibmcloud cos upload-dir \
  --bucket custodian-outputs \
  --key-prefix "$(date +%Y/%m/%d/%H%M%S)/" \
  --dir /tmp/c7n-out

10.Operational runbook

TaskCommand
Dry run (no actions taken) custodian run --configs ... --output-dir /tmp/dry --cache-period 0 --dryrun
Inspect matched resources cat /tmp/c7n-out/<policy-name>/resources.json | python3 -m json.tool
Find policies with matches grep -r '"count": [^0]' /tmp/c7n-out/*/metadata.json
Clear stale output before fresh run rm -rf /tmp/c7n-out
View Code Engine job logs ibmcloud ce jobrun logs --name <jobrun-name>
View webhook application logs ibmcloud ce application logs --name custodian-webhook --follow
Scale webhook under load ibmcloud ce application update --name custodian-webhook --min-scale 2 --max-scale 10 --concurrency 20
Rotate API key Create new key → update Secrets Manager secret → redeploy Code Engine job/app → delete old key
Rate limits. Each custodian run makes multiple IBM Cloud API calls. With --concurrency 20 on the webhook application, up to 20 runs may execute simultaneously. Keep concurrency at or below the number of parallel runs that fit within your account's API rate limit (~100 req/s per API key).
