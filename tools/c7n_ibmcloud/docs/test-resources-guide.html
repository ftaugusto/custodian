IBM Cloud Custodian — Test Resources Guide

IBM CLI commands to create non-compliant (policy fires) and compliant (policy does not fire) resources for every check across all 10 governance policy files.

Prerequisites

ibmcloud login --sso
ibmcloud target -r us-south -g Default

# Create a shared resource group for governance tests
ibmcloud resource group-create governance-tests
RG_ID=$(ibmcloud resource group governance-tests --output json | jq -r '.[0].id')

# Approved group (used by resource-group filter tests)
ibmcloud resource group-create approved-resource-group

# VPC base infrastructure
ibmcloud is vpc-create test-vpc --resource-group-name governance-tests
VPC_ID=$(ibmcloud is vpcs --output json | jq -r '.[] | select(.name=="test-vpc") | .id')
ibmcloud is subnet-create test-subnet $VPC_ID --zone us-south-1 --ipv4-prefix-length 24 --resource-group-name governance-tests
SUBNET_ID=$(ibmcloud is subnets --output json | jq -r '.[] | select(.name=="test-subnet") | .id')

# SSH key for instance tests
ibmcloud is key-create test-key "$(cat ~/.ssh/id_rsa.pub 2>/dev/null || ssh-keygen -t rsa -N '' -f /tmp/testkey -q && cat /tmp/testkey.pub)"
KEY_ID=$(ibmcloud is keys --output json | jq -r '.[] | select(.name=="test-key") | .id')

# Install Transit Gateway plugin (needed for transit gateway tests)
ibmcloud plugin install tg

# Export region
export REGION=us-south

1. IAM — iam.yaml

IAM resources (iam-user, iam-api-key, iam-access-group, iam-policy, iam-trusted-profile) do not support GlobalTaggingV1 — actions use custom non-tag mechanisms.

iam-user-mfa-disabledMUST
Non-compliant (policy fires)
# Invite a user — MFA is not enrolled by default.
# MFA enrollment cannot be forced via CLI; invite any new user.
ibmcloud account user-invite noncompliant-user@external.com
Compliant (policy does not fire)
# A user who has completed MFA enrollment in the IBM Cloud console
# will NOT be matched by the mfa-disabled filter.
# Verify via: ibmcloud account users --output json | jq '.[] | select(.iam_id!=null)'
# (No CLI command exists to enroll MFA — direct user to console Settings → MFA)

MFA status is set by the user in the IBM Cloud console. The policy flags any user where the MFA filter returns a match.

iam-user-suspendedSHOULD
Non-compliant (state ≠ ACTIVE)
# Suspend a user (requires account owner privileges):
ibmcloud account user-status-set suspended-user@example.com SUSPENDED
Compliant (state = ACTIVE)
# Active user — default state after accepting invitation:
ibmcloud account user-invite active-user@example.com
# Verify: ibmcloud account users --output json | jq '.[] | select(.state=="ACTIVE")'
iam-user-external-domainCAN
Non-compliant (email matches *@external.com)
ibmcloud account user-invite outsider@external.com
Compliant (internal domain)
ibmcloud account user-invite insider@yourcompany.com
iam-api-key-rotation-overdueMUST
Non-compliant (age > 180 days)
# Cannot back-date key creation. Use an existing key older than 180 days, or:
# For testing, create and note the date — policy fires after 180 days.
ibmcloud iam api-key-create old-test-key --description "Old key for custodian test"
Compliant (age ≤ 180 days)
ibmcloud iam api-key-create fresh-test-key --description "Fresh key for custodian test"

Time-dependent: age > 180 days cannot be simulated immediately. The non-compliant resource must be an existing key older than 180 days, or the test must be deferred.

iam-api-key-unlocked-past-rotation-ageMUST
Non-compliant (unlocked + age > 180 days)
# Same as above — requires an existing key older than 180 days that is not locked.
# Keys are unlocked by default.

# Do NOT lock it — this key must age past 180 days to trigger the policy.
Compliant (locked, or fresh)
ibmcloud iam api-key-create locked-key --description "Locked for compliance"
KEY_ID=$(ibmcloud iam api-keys --output json | jq -r '.[] | select(.name=="locked-key") | .id')
ibmcloud iam api-key-lock $KEY_ID

Time-dependent: same 180-day constraint as above.
